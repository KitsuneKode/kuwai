## B. Sandbox (`bin/rice_sandbox.py`, `sandbox/Dockerfile`)

One long-lived container, `rice-sandbox` (Debian trixie-slim: python3/pip, node/npm, git, curl, gcc, jq,
ripgrep, fd, headless Chromium; 1.19 GB). It runs as your uid with `--cap-drop ALL`, `no-new-privileges`,
a read-only root, `/tmp` as tmpfs, 2 GB memory, 4 CPUs, 512 processes; only
`~/.local/share/rice/sandbox` is mounted (at `/work`), each chat works in `/work/<chat>`, and `$HOME` is
`/work/.home` so `pip install --user` / npm packages persist. Network on (`RICE_SANDBOX_NET=none` turns it
off). Commands are killed after 120 s inside the container.

Because nothing in it can touch your system, `sandbox_run` / `sandbox_write` / `sandbox_read` need no
approval; `run_command` (your real machine) keeps the Run / Don't run card. Attached files are copied into
the chat's `files/` so code can work on the whole file. `rice-ollama sandbox status|build|stop|path`.

## C. Shopping (`shop_search`)

- Amazon.in answers a plain request with full search HTML: `data-component-type="s-search-result"` blocks,
  title in `h2[aria-label]`, price in the first `.a-offscreen`, MRP in the next, rating "4.1 out of 5
  stars", link `/dp/<ASIN>` (22 results measured).
- Flipkart builds results with JavaScript: rendered by the sandbox's Chromium (`--dump-dom`, ~13 s), then
  product cards found by `/p/itm…` links with the `₹` lines after them.
- DuckDuckGo results that are ads (`/y.js?ad_domain=…`, `result--ad`) are dropped; before, a shopping
  question got only ad links and hermes3 named 2018 laptops.
- `web_fetch` falls back to the rendered page when a page has under 800 characters of text or says "enable
  JavaScript".

## D. Rendering (from T3 Code, `docs/research` T3 study, this round)

What T3 Code does (apps/server ThreadLiveEventCoalescer, apps/web ChatMarkdown, markdown-incremental):
server-side 50 ms coalescing of whole snapshots; markdown cached up to the last closed fence; a stream
tokenizer for code that keeps finished lines; new blocks fade in (600 ms) only while streaming; follow the
bottom unless the user scrolls *up* (re-arm within 40 px); "Worked for Ns" folds; one-sentence tool
summaries; number keys 1–9 for question options. Weak spots: no reveal smoothing, full re-parse for
messages without fences, highlighting on the main thread, very complex timeline logic.

What we do now:

- Deltas fold into one update per frame (16 ms) in `OllamaService.flushDeltas`; anything else lands at once.
- Answers render block by block (`Turn.splitBlocks`: paragraphs, a loose list as one block, tables, code
  fences). A finished block's text never changes, so its delegate is left alone (declared QML properties
  only notify on a real change) and its HTML is rendered once by a long-running `rice-render --serve`
  (~1 ms a block) and cached by text. Only the block being written re-renders; `Turn.healTail` closes a
  half-written `**` or `` ` `` so it doesn't flash raw markers.
- The same HTML shows while streaming and after (no swap at the end); messages no longer store HTML.
- Code blocks highlight the moment their fence closes (plain while open).
- New blocks fade in over 260 ms while the answer streams, never when a chat opens.
- Following: only scrolling up lets go; within 40 px of the end picks the stream up again; the jump button
  doesn't flash while following.
- Tool groups say what happened: "Searched 2 times, read a page or file and ran a command".
